# Xingzhi 原版功能继续移植

## 摘要

继续将 Xingzhi 版本补齐到更接近原版 Clawdmeter 的日常体验和视觉体验，明确排除触摸交互。后续工作必须分阶段推进，每一阶段都先通过串口状态、截图回读或模拟动作验证，再进入下一阶段。

---

## 问题背景

Xingzhi 版本已经具备原版核心链路：240x240 三屏 UI、串口调试、BLE 用量传输、Windows BLE 工具、HID 快捷键和基础电源遥测。剩余差距主要集中在长期使用可靠性、蓝牙恢复、Clawd 动画体验、电量校准和部分硬件等价能力。

原版 Clawdmeter 的体验不只是显示用量。它还提供可恢复的蓝牙配对状态、由用量变化驱动的 splash 动画、动画自动轮换、明确的电量反馈，以及与实体按钮配合的日常交互。Xingzhi 硬件不同，不能直接搬运触摸、480x480 LVGL 或 Waveshare PMU 假设，但可以按 Xingzhi 的屏幕、按键和 Windows 主机路径继续补齐。

---

## 参与者

- A1. 用户：希望 Xingzhi 设备可长期日常使用，并尽量接近原版 Clawdmeter 的观感和交互。
- A2. Codex：通过串口调试、截图回读和模拟动作分阶段验证实体设备。
- A3. Xingzhi 设备：显示用量、状态和动画，处理 BLE、HID、按键、电源和恢复动作。
- A4. Windows 主机：负责长期获取 Claude 用量并通过 BLE 更新设备。
- A5. 后续规划/实现者：把本需求拆成多段计划，并在每段执行后保留验证证据。

---

## 关键流程

- F1. 分阶段移植与截图闸门
  - **触发条件:** 一个新移植阶段完成。
  - **参与者:** A2, A3, A5
  - **步骤:** 构建并刷写对应固件，查询串口状态，截图回读当前屏幕，必要时模拟按键或发送测试 payload，再确认阶段行为符合预期。
  - **结果:** 当前阶段可观察、可回归，后续阶段不会在未知设备状态上继续堆叠。
  - **覆盖:** R1, R2, R3, R4

- F2. 蓝牙恢复与日常连接
  - **触发条件:** Windows 无法稳定连接、配对缓存异常，或用户需要重新配对。
  - **参与者:** A1, A3, A4
  - **步骤:** 用户或调试命令触发蓝牙恢复动作，设备清理可恢复状态并重新广播，Windows 主机重新发现、连接并发送用量。
  - **结果:** 不需要重新刷机即可从常见 BLE 配对/缓存问题中恢复。
  - **覆盖:** R5, R6, R7, R8

- F3. 原版视觉体验还原
  - **触发条件:** 设备处于 splash 或用量更新到达。
  - **参与者:** A1, A3
  - **步骤:** 设备根据当前用量状态选择合适的 Clawd 动画，在 splash 上播放并自动轮换；实体切换键在 splash 上用于切换动画，在非 splash 屏幕上用于切换屏幕。
  - **结果:** Xingzhi 不再只是占位 splash，而是具备原版 Clawdmeter 的主要视觉识别。
  - **覆盖:** R9, R10, R11, R12

## Requirements / 需求

**阶段与验证**
- R1. 后续移植必须拆成多个阶段，每个阶段只交付一组可独立观察的能力。
- R2. 每个阶段完成后，必须先通过串口状态查询和截图回读验证当前屏幕，再进入下一阶段。
- R3. 交互相关阶段必须通过串口模拟动作或实体按键验证，确认不会破坏已完成的用量显示、BLE 或 HID 行为。
- R4. 每个阶段的 plan 必须写明该阶段的串口验证闸门和人工验收点。

**蓝牙恢复与主机可靠性**
- R5. Xingzhi 必须提供可触发的 BLE 配对清理或恢复路径，替代原版触摸 reset zone。
- R6. BLE 恢复能力必须能通过串口调试触发，并在设备屏幕上显示可理解的恢复状态。
- R7. Windows 主机路径必须从手动一次性发送推进到可长期运行的模式，覆盖发现、连接、重连、发送成功和发送失败。
- R8. Windows 长期运行第一版采用命令行 watch 模式，不要求第一阶段具备 GUI、安装器或开机自启，但必须能产生日常排障所需的清晰日志。

**Splash 与视觉还原**
- R9. Xingzhi splash 必须从占位图推进到 Clawd 动画播放体验。
- R10. Splash 动画必须能根据当前用量状态或用量变化选择不同强度/类别的动画。
- R11. Splash 必须支持自动轮换，避免长时间停留在同一动画。
- R12. 实体切换键在 splash 上应优先切换动画；在非 splash 屏幕上继续承担屏幕切换职责。

**电源与硬件等价**
- R13. 电池和充电显示必须继续校准，至少覆盖 USB 供电、充电中和非充电状态的可观察差异。
- R14. 如果主机侧可见电量状态可用，它应尽量反映设备实际电量，而不是固定值。
- R15. IMU 自动旋转属于候选移植项，但必须先验证 Xingzhi 硬件是否提供可用传感器；不可用时不阻塞其他阶段。

**兼容与回归**
- R16. 已完成的串口 fallback、BLE GATT、HID 快捷键、三屏 UI、截图回读和基础电源遥测必须保持回归可用。
- R17. 新增能力应继续进入 Xingzhi parity 路径，不应把完整功能塞回显示 bring-up 或最小串口仪表目标。
- R18. 默认 Waveshare 原版目标不能因为 Xingzhi 继续移植而被破坏。

## Acceptance Examples / 验收示例

- AE1. **覆盖 R1, R2, R4。** 前提是一个阶段实现完成，当执行该阶段计划中的串口状态查询和截图回读时，应能看到该阶段新增能力的可观察结果，并记录为继续下一阶段的依据。
- AE2. **覆盖 R5, R6。** 前提是 Windows 配对或连接异常，当通过串口触发 BLE 恢复时，设备应重新进入可发现/可连接状态，屏幕或状态输出显示恢复结果。
- AE3. **覆盖 R7, R8。** 前提是 Windows 长期运行工具已启动，当 BLE 短暂断开后恢复时，工具应能记录断开、重连和后续发送结果。
- AE4. **覆盖 R9, R10, R11。** 前提是设备停在 splash，当用量状态变化或等待自动轮换周期时，截图回读应能观察到 Clawd 动画状态变化。
- AE5. **覆盖 R12。** 前提是设备停在 splash，当模拟或按下切换键时，行为应是切换动画；前提是设备停在 usage 或 status，当执行同一动作时，行为应是切换屏幕。
- AE6. **覆盖 R13, R14。** 前提是设备处于不同供电/充电状态，当查询串口状态并截图 status 屏时，电源状态应表现为可解释的差异，而不是不可用或固定假值。
- AE7. **覆盖 R16, R17, R18。** 前提是新阶段完成，当运行既有串口 fallback、BLE payload 和 HID 验证时，已完成能力应仍可用，且非 Xingzhi 目标未被破坏。

---

## 成功标准

- Xingzhi 能在日常使用中更可靠地连接、恢复和接收 Windows 主机用量更新。
- 用户能看到接近原版 Clawdmeter 的 Clawd splash 动画体验，而不只是静态占位屏。
- 电源状态在真实硬件上可解释，并能为日常使用提供可信参考。
- 每个阶段都有串口截图、状态或动作验证记录，后续 planning 不需要重新发明验证流程。
- 触摸交互被明确排除，不会在计划或实现中反复引入硬件不匹配的假设。

---

## Scope Boundaries / 范围边界

- 不实现触摸交互，包括触摸切换 splash、触摸关闭 splash 和触摸 reset Bluetooth。
- 不要求第一阶段完成 Windows GUI、托盘、安装器、服务或开机自启。
- 不把 USB 串口 fallback 作为日常用量传输主路径；它仍是调试和救援路径。
- 不把 `xingzhi_display_bringup` 或 `xingzhi_serial_meter` 扩展成完整功能目标。
- 不为了 Xingzhi 移植重构默认 Waveshare 应用，除非共享逻辑维护确有必要并能回归验证。
- 不因 IMU 或电源硬件能力不确定而阻塞 BLE 恢复、Windows 长期运行或 splash 动画阶段。

---

## 关键决策

- 分阶段推进：剩余功能同时包含可靠性和视觉体验，一次性落地会让实体设备排障成本过高。
- 截图闸门优先：Xingzhi 已具备串口截图能力，后续每段都应利用它降低人工观察成本。
- 触摸替代而非移植：原版触摸 reset 和 splash 切换能力在 Xingzhi 上应改由串口、按键或状态屏入口承载。
- Windows 长期运行先用命令行 watch 模式：这是最快能验证发现、连接、重连、日志和持续发送稳定性的路径；后台任务、托盘或服务形态后置。
- 日常可靠性与视觉还原都纳入范围：蓝牙恢复、Windows 长期运行和动画体验分别解决可用性与产品识别，不应互相排除。
- 硬件等价以实际 Xingzhi 能力为准：电源和 IMU 只做可验证能力，不强行复制 Waveshare 板级实现。

---

## 依赖与假设

- 当前 Xingzhi parity 能力继续可用：串口调试、截图、模拟按键、BLE GATT、HID、三屏 UI 和基础电源遥测。
- Windows Python、pyserial、esptool 和 BLE 依赖可继续用于刷写与调试。
- Xingzhi 屏幕尺寸仍以 240x240 为约束，视觉还原需要接受紧凑布局。
- 原版 Clawdmeter 动画资源可以继续作为视觉还原基线，但具体适配方式留给 planning。
- 用户愿意在关键阶段执行人工验收，例如蓝牙恢复、长期运行、实体按键和不同供电状态。
